# Phase PERF — la performance, **mesurée** (2026-10-23)

*Plan de la phase suivante. Suite de `docs/ab/phase8-2026-10-23.md` (AB8),
qui a tranché vers l'issue **C** : « la porte ne porte pas sur
l'algorithme », le goulot est la **fonction de valeur**.*

---

## 1. Pourquoi cette phase, et à quelle condition

La phase AB8 a établi deux choses qu'il faut tenir ensemble :

1. **La force ne vient pas de l'heuristique d'élagage.** Sur une valeur
   bruitée, aucune ne paie : le null-move perd 71 Elo au duel, le LMR est
   neutre, la razoring et la futilité sont inertes. Un moteur ne gagne
   pas des Elo en descendant plus vite dans un arbre bruité.
2. **La valeur apprise est la seule voie** (phase NN, AB6). Mais une
   valeur apprise ne sert que si la recherche a le **débit** pour
   l'exploiter : à 200 ms, l'alpha-beta de ce dépôt ne descend qu'à la
   profondeur 4, et le MCTS plafonne à ~700 k playouts/s.

C'est là que la performance est un **prérequis** et non un levier de
force : *la phase NN a un plafond de débit, et ce plafond est une
question de performance*. Pour viser 3000 Elo, il faut des **millions
de nœuds/s** en alpha-beta, et des **dizaines de milliers** de
suspensions/s en MCTS avec réseau — donc, en CPU-only (Tier D, pas de
GPU), une évaluation **par lot** (SIMD) et un arbre **partagé**.

**La condition de la phase** : une optimisation n'est acceptée que si
elle est **mesurée** (jamais devinée) et qu'elle ne change **ni la
valeur, ni les résultats de recherche** — sinon, elle impose de
re-geler les mesures gelées des phases 3 à 5, ce qui coûte plus qu'elle
ne rapporte. Cette discipline est celle du dépôt depuis le début
(`docs/analyse_movegen_mcts.md`, `docs/movegen/phase2-2026-10-21.md`).

> **Ce que la phase n'est pas** : une phase « force ». Aucun de ses
> livrables ne doit déplacer l'Elo. Si un slice déplace l'Elo, c'est
> qu'il a changé le moteur — il est alors traité comme un changement
> de phase (re-gel + rapport), pas comme une optimisation.

---

## 2. La ligne de base (mesurée, pas supposée)

L'instrument est `examples/perf_probe.rs`. Il mesure les cinq chemins
chauds dans une seule session, sur un corpus **déterministe** (4
positions de référence + 60 positions d'une marche aléatoire à graine
fixe), et sort en `PROF|<section>|<métrique>|<valeur>`.

**Hôte de cette mesure** : WSL2, 12 threads, `Ryzen 5 1600X`-like.
**Ce n'est pas l'hôte de référence** (`EPYC 7763`) : ces chiffres
servent d'**ordre de grandeur relatif** (A/B/A/B même session), pas de
mesure de référence. Toute valeur future est à reprendre sur l'EPYC.

| chemin | mesure | baseline (2026-10-23, avant) |
|---|---|---|
| `eval` | `eval_for_mover` (la feuille des deux algorithmes) | **106,5 ns** / appel |
| `movegen` | `generate(All)` — 32 coups | **187,1 ns** / appel |
| `movegen` | `generate(CapturesOnly)` — 7 coups | 85,0 ns / appel |
| `makeunmake` | make + unmake | 20,4 ns / paire |
| `ab` | alpha-beta, profondeur 5 (kiwipete) | 1 102 522 nœuds, 470 ms → **2,35 Mnps**, **426 ns/nœud** |
| `ab` | alpha-beta, budget 200 ms | 465 920 nœuds, **418 ns/nœud**, profondeur 4 |
| `mcts` | MCTS mono (200 k playouts) | 597 k playouts/s, **1675 ns/playout**, 20 917 nœuds, 863 208 arêtes |
| `mcts` | MCTS 4 threads | 1,87 M playouts/s (535 ns/playout, ×3,1) |

Trois lectures immédiates :

* **le core n'est pas le goulot** : `perft` fait 219–257 Mnps (le
  movegen seul, sans la boîte aux lettres) ; la recherche fait 2,35
  Mnps. Le core est **gelé** et il n'est pas là qu'il faut aller ;
* **l'alpha-beta paie deux choses** : le movegen (187 ns) et l'éval
  (106 ns), soit **69 %** du coût d'un nœud (426 ns) ;
* **le MCTS est un problème de mémoire, pas de calcul** : 863 208
  arêtes à 20 octets = **17 Mo** d'arène pour 20 917 nœuds, et la
  sélection parcourt 41 arêtes par nœud. C'est le « goulot de marche
  mémoire » déjà identifié le 2026-10-21
  (`docs/analyse_movegen_mcts.md` §1.2 : ~70-80 cache misses par
  simulation, nps qui chute de 468 k à 327 k quand l'arbre grandit).

## 3. Les cinq familles d'optimisations, confrontées au code réel

Une liste générique (« PEXT, prefetch, lock-free, SIMD, branchless »)
n'est pas un plan : chaque item doit être confronté à **ce que fait
déjà ce dépôt**. Verdict :

| famille | dans ce dépôt | verdict |
|---|---|---|
| **Bit-twiddling / PEXT** | **déjà fait** : le chemin PEXT est actif (`chemin pext actif` dans le README), avec un repli *magic* portable ; le movegen est à 219–257 Mnps | le levier restant est **l'évaluation**, qui scanait 64 cases : **fait (P2)** |
| **Hiérarchie de cache / prefetch** | **le vrai goulot du MCTS** : 17 Mo d'arête, 41 arêtes par nœud dans la sélection | **slice P4** (à mesurer : misses/simulation avec `perf`) |
| **False sharing** | **sans objet aujourd'hui** : chaque worker MCTS a son **propre** arbre (`run_worker` → `Arena` par worker), la fusion se fait à la racine | redevient le **problème central** de P5 (arbre partagé) → `alignas(64)` sur les compteurs atomiques |
| **Lock-free / atomiques / XOR hashing** | le XOR hashing (Zobrist) est déjà là ; la TT de l'alpha-beta est **mono-thread** (un `Vec`, aucun verrou) | P5 exigera des atomiques *relaxed* ; le vrai manque n'est pas le verrou, c'est l'**arbre partagé** |
| **SIMD / batching** | aucun réseau, donc aucun lot | **hors périmètre** : c'est la phase NN. Mais la phase doit **préparer l'interface** (évaluation par lot) — voir P6 |
| **Branchless** | l'éval avait une branche par case (« case vide ? »), le taux de prédiction ratée est de ~50 % | **fait (P2)** ; reste la sélection PUCT (argmax) et l'ordre des coups |

**La conclusion de ce tableau** : deux des cinq familles sont déjà
faites, une ne s'applique pas encore, une est hors périmètre, et une
(la cache) est **le** goulot du MCTS. Le plan ne « réinvente » rien : il
suit la mesure.

---

## 4. Les tranches, dans l'ordre

Chaque tranche a un **gate** : la mesure qui décide de la garder.

### P0 — l'instrument et la ligne de base — **FAIT**

`examples/perf_probe.rs` (le tableau §2). Sans lui, toute optimisation
serait une intuition. *Gate* : le corpus est déterministe, la sortie
est machine-lisible, et deux exécutions sur la même machine sont
comparables.

### P1 — l'alpha-beta sans allocation par nœud — **FAIT**

Chaque nœud allouait un `Vec<(i32, Move)>` (malloc + free + le tampon
temporaire du tri stable) : à un million de nœuds, un million
d'allocations. Le correctif : les scores vivent dans un tampon **par
ply** (alloué une fois par recherche), l'ordre est un tableau
d'**indices** `u8` sur la pile, et le tri est *instable* — mais sur un
ordre **total** (score décroissant, puis indice croissant), donc
**identique** au tri stable d'avant.

*Gate* : **le nombre de nœuds à profondeur 5 est inchangé** — 1 102 522
avant et après. C'est la preuve que la recherche est bit-à-bit
identique.

### P2 — l'évaluation sans la boîte aux lettres — **FAIT**

`eval_white` parcourait les **64 cases** de la mailbox, avec une
branche « case vide ? » par case (~50 % de prédictions ratées). La
version bitboard ne visite que les cases **occupées** (~32), sans
branche, et la table PST est **fusionnée** avec le matériel (une seule
lecture par pièce, plus de `popcount` séparé).

*Gate* : un test d'identité compare la nouvelle valeur à l'ancienne
(boîte aux lettres) sur **4 000 positions** — la valeur est **identique
au bit**. Corollaire : les mesures gelées des phases 3 à 5 (MCTS) et de
la phase AB restent **reproductibles**, ce que confirme le MCTS :
`tree_nodes` = 20 917 et `tree_edges` = 863 208, avant comme après.

### P3 — la génération de coups **échelonnée** dans l'alpha-beta — *à faire*

`generate(All)` coûte 187 ns contre 85 ns pour `generate(CapturesOnly)`.
Or la quasi-totalité des nœuds alpha-beta **coupent** (fail-high) sur
un coup qui n'est pas le premier : on génère 32 coups pour en tester
un. Le correctif classique est la **génération en deux temps** : les
captures d'abord, et les coups tranquilles seulement si aucun coup n'a
coupé.

*Ce slice change le nombre de nœuds* (l'ordre des coups reste le
même, mais l'ensemble des coups testés à chaque nœud change) : il
impose donc de **re-geler** la référence alpha-beta et de rejouer le
duel de la phase AB8. *Gate* : gain de débit **mesuré** (ns/nœud) et
**duel rejoué** (400 parties, SPRT, contrôle inclus) pour vérifier que
la force n'a pas bougé.

### P4 — la compacité de l'arène MCTS — *à faire*

L'arête est un `Edge` de 20 octets ; la sélection lit `visits`, `sum`,
`prior` (12 octets utiles) et ignores `mv`/`child` (6 octets) — le
reste est un motif de cache gaspillé. Correctif : **séparer le chaud du
froid** (un tableau `EdgeHot` de 12 octets pour la sélection, un
`EdgeCold` pour le mouvement et l'enfant), puis, si le profil le
confirme, un **préfetch** explicite de l'arête suivante pendant le
balayage.

*Gate* : la structure de l'arbre doit rester **identique**
(`tree_nodes`, `tree_edges` et les coups choisis inchangés) — le gain
est purement mémoire ; et le nombre de **cache misses** par simulation
doit être mesuré (`perf stat -e cache-misses`) avant et après.

### P5 — l'arbre MCTS partagé, lock-free — *à faire, risque élevé*

Aujourd'hui, chaque worker a son **propre** arbre et la fusion se fait
à la racine : les workers **n'apprennent rien** du travail des autres
pendant la recherche. C'est la limite structurelle du MCTS actuel, et
c'est *là* que le « false sharing » et les « atomiques » de la liste
generic deviennent le sujet : un arbre partagé, des compteurs atomiques
`Relaxed` par arête, alignés sur 64 octets, et une stratégie
d'attribution (qui met à jour quelle arête) pour éviter les conflits
d'écriture.

*Ce slice change la recherche* (les résultats, donc la force) : il
impose un re-gel complet des phases 3 à 5 et un rapport propre. *Gate* :
gain de playouts/s **et** force (SPRT contre la référence gelée) — un
gain de débit qui coûte de la force est un échec.

### P6 — l'évaluation par lot (SIMD) — *la phase NN, hors périmètre ici*

Le lot (batch) n'a de sens qu'avec un **réseau** : c'est la phase AB6.
Mais la phase PERF doit en préparer l'**interface** : la feuille doit
être évaluable **par lot** (256 positions d'un coup), et l'arbre doit
être capable d'être **partagé** (P5) — sans quoi le lot n'a pas de
source. C'est pourquoi P5 n'est pas optionnel : c'est le **prérequis
architectural** du lot.

## 5. Les résultats des tranches faites (P0–P2)

Mesures A/B/A/B sur la même machine, dans la même session.

| métrique | avant | après | gain |
|---|---|---|---|
| `eval_for_mover` | 106,5 ns | **30,6 – 34,4 ns** | **×3,1** |
| alpha-beta, profondeur 5 | 2,35 Mnps (426 ns/nœud) | **3,34 – 3,39 Mnps** (295–299 ns/nœud) | **+43 %** |
| alpha-beta, nœuds en 200 ms | 465 920 | **622 592 – 679 936** | **+34 à +46 %** |
| MCTS mono | 597 k playouts/s (1675 ns) | **675 – 735 k** (1360–1480 ns) | +13 à +23 % |
| MCTS 4 threads | 1,87 M playouts/s | **2,44 – 2,53 M** | +30 à +35 % |

**Identité vérifiée** :

| invariant | avant | après |
|---|---|---|
| alpha-beta, nœuds à profondeur 5 | 1 102 522 | **1 102 522** |
| MCTS mono, `tree_nodes` | 20 917 | **20 917** |
| MCTS mono, `tree_edges` | 863 208 | **863 208** |
| MCTS 4 threads, `tree_nodes` / `tree_edges` | 15 791 / 644 779 | **15 791 / 644 779** |
| `eval_white` (bitboard) vs boîte aux lettres | — | **identique** sur 4 000 positions |

Les gains sont **gratuits en force** : les recherches sont bit-à-bit
identiques, donc les mesures gelées des phases 3 à 5 et de la phase AB
restent valides, et aucun duel n'a besoin d'être rejoué.

## 6. Les invariants de la phase (la barre)

1. **Mesurer avant d'optimiser** : pas de slice sans la mesure
   correspondante dans `examples/perf_probe.rs` (ou `perf`), avant et
   après, sur la même machine, en A/B/A/B.
2. **Bit-identité par défaut** : une optimisation qui change la valeur
   ou les résultats de recherche doit le dire, re-geler la référence
   correspondante, et rejouer le duel de force. Le chemin par défaut
   ne change pas sans un rapport.
3. **Le core reste gelé** (`vcore-1.0`) : pas de refactoring du
   movegen, de `make`/`unmake`, des tables ou du format de coup sans
   un bug prouvé — et, dans ce cas, une revalidation perft + la
   réconciliation d9.
4. **Pas de `unsafe` pour gagner 5 %** : le dépôt n'a pas d'`unsafe`
   dans le cœur de l'arbre ; l'introduire pour une micro-optimisation
   n'est pas justifié par la mesure.
5. **Pas de seuil nps en CI** : l'hôte de mesure est partagé et
   bruité ; le CI vérifie des **invariants**, pas des performances.
6. **La portability** : le dépôt a un repli *magic* pour ARM/WASM ; une
   optimisation ne peut pas casser ce repli (`target-cpu=native` est
   exclu : le binaire doit rester portable).

---

## 7. Ce que la phase ne fait pas

* **Pas de réseau de neurones** (c'est P6 / la phase NN).
* **Pas de GPU** (Tier D : CPU-only).
* **Pas de changement du movegen** : il est à 219–257 Mnps, ce n'est pas
  le goulot, et le core est gelé.
* **Pas de « force »** : aucun slice de cette phase ne doit faire
  gagner de l'Elo ; s'il en gagne, c'est un changement de moteur.
* **Pas de seuil de nps figé** dans le code ou le CI.

---

## 8. La suite

1. **P3** (génération échelonnée) et **P4** (arène compacte) : les deux
   gains qui restent, à périmètre connu ;
2. **P5** (arbre partagé lock-free) : le seul changement qui touche à
   la **force** du MCTS — et le prérequis du lot ;
3. **P6 / phase NN** (AB6) : la valeur apprise, par lot, avec l'interface
   préparée par P4-P5.

## 9. Reproduction

```bash
# l'instrument et la ligne de base
cargo run --release --example perf_probe

# le test d'identité de l'évaluation (la valeur est bit-à-bit identique)
cargo test --release --lib eval

# les tests d'invariants de l'alpha-beta (dont « le défaut est inchangé »)
cargo test --release --test alpha_beta_heuristiques
```
