# Phase NN — la valeur apprise, par lot (2026-10-23)

*Plan de la phase. Suite de `docs/perf/plan-perf-2026-10-23.md` (phase
PERF) et de `docs/ab/phase8-2026-10-23.md` (AB8, qui a tranché vers
l'issue **C** : « la porte ne porte pas sur l'algorithme »).*

*Le compte rendu de la phase (mesures, verdicts, leçons) est dans
`docs/nn/phase-nn-2026-10-23.md`. Ce document est le **plan** : ce qui
était prévu, et ce qui a été fait.*

---

## 1. Pourquoi cette phase, et pourquoi maintenant

AB8 a établi, **mesuré**, que :

* le goulot d'étranglement du projet n'est pas l'algorithme de
  recherche mais la **fonction de valeur** (erreur ≈ 490 cp, instabilité
  ≈ 104 cp / 2 plies) ;
* sur une valeur aussi bruyante, **aucune** heuristique d'élagage ne
  paie en force : le null-move perd 71 Elo au duel, le LMR est neutre,
  razoring et futilité sont inertes ;
* le bruit **casse** l'élagage de l'alpha-beta (facteur 100 000× sur une
  position), donc un alpha-beta sans valeur fiable ne peut pas
  approfondir.

La phase NN est donc **la** voie. Mais elle n'est utile que si le
débit suit : c'est ce que la phase PERF vient de fournir (+43 % sur
l'alpha-beta, ×3,1 sur l'évaluation) et ce qu'elle doit encore fournir
avant que le lot ait un sens (arène compacte P4, arbre partagé P5).

**La condition de la phase** : la valeur apprise doit **remplacer** la
feuille statique, pas l'expliciter à côté. Le test de la phase est un
**duel de force** (SPRT, 400 parties, contrôle inclus) contre la
référence gelée — exactement le protocole de la phase AB8, dont on sait
maintenant qu'il a une résolution de ± 30 Elo et qu'il **s'auto-démonte**
s'il n'est pas précédé d'un contrôle.

---

## 2. Ce que la phase fait — et ne fait pas

| fait | ne fait pas |
|---|---|
| une **interface d'évaluation par lot** (le contrat que le lot SIMD exigera) | pas de GPU (Tier D, CPU-only) |
| un **collecteur de positions** (self-play → corpus d'entraînement) | pas de changement du core gelé |
| un **modèle de valeur** (petit NN, CPU, inférence SIMD) | pas de politique (le MCTS garde ses priors heuristiques) |
| le **câblage** de la feuille : MCTS et alpha-beta consomment la même valeur | pas de ré-écriture de l'alpha-beta (il reste l'instrument de mesure) |
| la **mesure de force** par duel SPRT contre la référence gelée | pas de modification du protocole de mesure (gelé) |

## 3. Les tranches

### N-1 — le correctif du générateur — *FAIT*

Ce n'était pas au plan : c'est un **bug trouvé en exécutant le plan**.

Le générateur du MCTS (`mcts::Rng`, un xorshift64\* annoncé) avait le
triple de décalages `>> 12 ; >> 25 ; >> 27` au lieu du triple
canonique `>> 12 ; << 25 ; >> 27`. Le décalage du milieu doit être à
**gauche** : avec trois décalages à droite, la transformation de l'état
n'est pas réversible, et le générateur avait une **période de 4** — il ne
produisait que **quatre** valeurs, répétées indéfiniment.

*Gate* : un test de non-répétition (10 000 tirages distincts) +
un test de déterminisme. Les deux sont dans `src/mcts.rs`.

*Ce que le bug invalidait* : le tirage « au hasard » du MCTS (le choix
parmi les enfants non visités) et la perturbation Gumbel de la racine ne
tiraient que quatre valeurs. Le corpus d'auto-play de la tranche N1
n'avait **aucune** diversité — et le réseau de valeur n'apprenait
strictement rien (il n'y avait pas de signal, seulement quatre positions
à caser). C'est en cherchant à entraîner le réseau que le bug est
apparu.

*Ce que le bug ne touche pas* : le core gelé (`vcore-1.0`) ne contient
aucun générateur — `position`, `movegen`, `types` et `zobrist` sont
inchangés. En revanche le **comportement du MCTS change**, donc les
mesures gelées des phases 3 à 5 ne sont plus reproductibles avec ce
binaire : c'est un **changement de moteur**, et il est mesuré par un
duel comme tel (voir le compte rendu).

### N0 — l'interface par lot — *FAIT*

`eval::eval_batch(&[Position]) -> Vec<i32>` : la même valeur que
`eval_for_mover`, position par position, mais appelée **par lot**. C'est
le seul contrat dont l'inférence SIMD a besoin : le lot est évalué par
position, et le réseau est appliqué au lot.

*Gate* : `eval_batch` rend **exactement** les mêmes valeurs que
`eval_for_mover` sur le même corpus (test d'identité, comme pour P2). —
**PASSÉ** (`src/eval.rs`).

### N1 — le collecteur de corpus — *FAIT*

`examples/gen_positions` : self-play du moteur (MCTS), avec une graine
fixe, et dump des positions (zobrist + FEN + résultat + ply + partie)
dans un format texte stable. C'est le corpus d'entraînement — et, en
même temps, un **outil de mesure** : il donne la distribution des
positions que le moteur visite réellement (pas un corpus de positions
« d'échecs »).

*Deux règles d'honnêteté*, inscrites dans le code :

1. une partie qui **n'a pas de résultat** (limite de demi-coups
   atteinte) est **jetée** : l'arbitrer avec l'évaluation statique
   reviendrait à écrire la réponse dans la question — le réseau
   apprendrait l'évaluation statique, et la mesure « le réseau vaut
   mieux que l'éval statique » n'aurait plus de sens ;
2. la seule annotation est le **résultat de la partie** — pas la valeur
   d'une recherche (elle est bruitée : c'est mesuré, phase AB7).

*Gate* : sortie **déterministe** (même graine → même fichier), et le
corpus est **rejouable** (le FEN se relit et la position se
reconstitue). — **PASSÉ** (deux exécutions → fichiers identiques ;
aller-retour FEN testé dans `src/corpus.rs`).

### N2 — le modèle de valeur — *FAIT*

Un petit réseau **CPU-only**, CPU-only, sans dépendance :
`src/nn.rs`.

* **Entrée** : l'échiquier, en **forme creuse** — 12 plans de pièces
  (6 genres × 2 couleurs), dont seules les ~32 cases occupées sont
  lues, plus une feature « trait ».
* **Couche cachée** : 64 unités, ReLU. La première couche est donc une
  **table de positions apprise** (chaque pièce sur chaque case
  contribue une ligne de poids).
* **Sortie** : un scalaire **linéaire**, dans l'échelle de la valeur
  (±1), découpé à l'inférence.
* **Paramètres** : 49 345 (12 × 64 × 64 + le reste) — « quelques
  dizaines de milliers », comme prévu.
* **Inférence SIMD** : AVX2 **détecté à l'exécution**, avec repli
  scalaire (le résultat est **identique** dans les deux cas : c'est le
  même ordre d'addition). Pas d'AVX-512 : l'EPYC de référence n'en a
  pas.
* **Format de fichier** : versionné, portable, avec aller-retour testé.

*Gate* : l'erreur de la valeur sur un corpus de test **gelé** doit être
**nettement meilleure** que celle de l'éval statique **calibrée** —
c'est le gate *technique* ; le gate de *force* est le duel de la tranche
N4.

### N3 — l'entraînement — *FAIT*

Entraînement hors ligne sur le corpus de N1, avec des positions
annotées par le **résultat de la partie**. L'optimiseur est **Adam**,
écrit dans l'exemple (aucune dépendance) ; la découpe train/test est
**par partie** (jamais par position : sinon les positions d'une même
partie se répondent mutuellement et la mesure d'erreur est une
illusion).

*Gate* : la RMSE de validation **descend** et le réseau bat l'évaluation
statique calibrée sur le corpus de test.

*Instrumentation* : la vérification numérique du gradient
(`--check-grad`) — le gradient analytique est comparé au gradient par
différences finies. Elle a trouvé un **défaut** (la ReLU n'était pas
appliquée avant la couche de sortie dans le backward : l'entraînement
optimisait une fonction *différente* de celle déployée, et le gradient
ne correspondait à rien). Sans elle, on aurait cherché un réglage de
taux d'apprentissage au lieu d'un défaut.

### N4 — le duel de force — *le gate de la phase*

La valeur apprise entre dans la feuille (MCTS **et** alpha-beta, via un
point de câblage unique : `nn::leaf_cp`), puis le duel : **SPRT gelé**
(`elo0=0 elo1=5 alpha=0.05 beta=0.05`), 400 parties, contrôle inclus,
sur le moteur de référence gelé. L'option UCI `EvalNN` (0 par défaut)
sépare les deux moteurs : le « B » est le **même binaire**, sans la
valeur apprise.

*Gate* : le LLR atteint la borne d'acceptation (+2,94) — c'est-à-dire
une **amélioration prouvée** à 95 % de confiance. Une valeur apprise
qui n'améliore pas la force est un échec de la phase, même si son
erreur d'évaluation est meilleure : c'est exactement la leçon d'AB8
(le null-move passait les mesures d'instrument et perdait au duel).

## 4. Les risques, et ce qu'on fait s'ils se réalisent

| risque | signal | réponse |
|---|---|---|
| la valeur apprise est meilleure en **erreur** mais pas en **force** | le duel N4 est plat | ne pas l'adopter : le MCTS/AB **amortit** le bruit, l'AB l'**amplifie** — c'est le résultat d'AB1, il se reproduira |
| l'entraînement sur les positions du moteur **sur-apprend** l'éval statique | l'erreur de validation remonte | re-collecter (self-play avec la **nouvelle** valeur), comme dans AlphaZero |
| le lot SIMD ne change rien (le réseau est trop petit) | le débit par lot ne progresse pas | le réseau n'est pas le goulot : c'est la **marche mémoire** de l'arbre (P4/P5) |
| la phase déborde | — | chaque tranche a son gate ; une tranche qui ne passe pas son gate s'arrête là, elle ne contamine pas la suivante |

---

## 5. Les invariants de la phase

1. **Le core reste gelé** (`vcore-1.0`) : le réseau lit la position, il
   ne la modifie pas ; aucune API du core ne change. Le correctif du
   générateur (N-1) est **hors core** : `mcts::Rng` n'appartient pas au
   core gelé, et le bug est *prouvé* par un test.
2. **La convention de signe ne change pas** : positive = le trait est
   meilleur, comme `eval_for_mover` aujourd'hui. Tout test qui compare
   les deux doit continuer d'avoir un sens.
3. **Le protocole de mesure est gelé** : `test.sh`, le SPRT
   `elo0=0 elo1=5 alpha=0.05 beta=0.05`, le contrôle obligatoire avant
   chaque duel.
4. **Bit-identité par défaut** : la valeur statique reste disponible et
   est la **référence** ; le réseau est *câblé* (`EvalNN=1`), pas
   *substitué*, tant que la phase ne l'a pas décidé.
5. **Déterminisme** : à graine fixée, la phase est rejouable (le
   corpus, l'entraînement et l'inférence sont déterministes).

## 6. Reproduction

```bash
# N0 : le contrat par lot (identité des valeurs)
cargo test --release --lib eval

# N-1 : le générateur (période longue, déterminisme)
cargo test --release --lib mcts::tests

# N1 : le collecteur de corpus (déterministe)
cargo run --release --example gen_positions -- 2000 /tmp/corpus.txt
cargo run --release --example gen_positions -- 2000 /tmp/corpus2.txt
cmp /tmp/corpus.txt /tmp/corpus2.txt   # identique

# N2/N3 : l'entraînement (avec la vérification du gradient)
cargo run --release --example train_nn -- models/corpus_v2.txt models/value_v1.bin \
    --check-grad
cargo run --release --example train_nn -- models/corpus_v2.txt models/value_v1.bin \
    --epochs 30 --lr 0.003

# N4 : le duel (SPRT gelé, contrôle inclus)
tools/duel_nn.sh --controle --rounds 200 --sprt --out prt/rr/nn-controle.log
tools/duel_nn.sh --rounds 200 --sprt --out prt/rr/nn-duel.log \
    --net models/value_v1.bin

# l'instrument de performance (la phase PERF reste la reference)
cargo run --release --example perf_probe
```

## 7. La suite

* **PERF P3/P4/P5** (génération échelonnée, arène compacte, arbre
  partagé) : le lot a besoin de P4 et P5 pour avoir une source, et la
  valeur apprise coûte déjà 18 % de débit à la feuille ;
* **NN N4** : le verdict du duel ;
* puis, et seulement, la **politique** apprise (le MCTS avec un réseau
  qui donne aussi les priors), qui est la voie des 3000 Elo.
