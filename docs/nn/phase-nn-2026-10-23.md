# Phase NN — la valeur apprise : compte rendu (2026-10-23)

*Le plan est dans `docs/perf/plan-nn-2026-10-23.md`. Ce document est le
**compte rendu** : ce qui a été fait, ce qui a été mesuré, ce qui a
échoué, et ce qu'on en retient.*

---

## 1. Le résumé, en une page

La phase NN devait remplacer la **fonction de valeur** du moteur — le
goulot établi par la phase AB8 (erreur ≈ 490 cp, instabilité ≈ 104 cp
par 2 plies) — par une valeur **apprise**, en mode **par lot** (le
contrat que le SIMD exigera).

Ce qui a été fait :

| tranche | quoi | gate | verdict |
|---|---|---|---|
| **N-1** | correctif du générateur du MCTS (période de 4 !) | non-répétition + déterminisme | **PASSÉ** |
| **N0** | `eval::eval_batch` — le contrat par lot | identité avec `eval_for_mover` | **PASSÉ** |
| **N1** | `examples/gen_positions` — le collecteur de corpus | déterminisme + rejouabilité | **PASSÉ** |
| **N2** | `src/nn.rs` — le modèle de valeur (CPU-only, AVX2) | — | **FAIT** |
| **N3** | `examples/train_nn` — l'entraînement (Adam, sans dépendance) | RMSE de test < RMSE de l'éval statique calibrée | **PASSÉ** |
| **N4** | `tools/duel_nn.sh` — le duel de force (SPRT gelé) | LLR ≥ +2,94 | **en cours** |

Trois choses ont été apprises en route, et elles sont plus importantes
que le résultat :

1. **le générateur du MCTS ne tirait que quatre valeurs** (le bug N-1) ;
   sans lui, le corpus n'avait aucune diversité et le réseau
   n'apprenait rien — pas « mal », **rien** ;
2. **le backward de l'entraînement n'était pas le backward du
   réseau déployé** (la ReLU manquait avant la couche de sortie) :
   l'optimiseur optimisait une autre fonction ; c'est la vérification
   numérique du gradient qui l'a montré, pas la courbe de perte ;
3. **une perte qui descend n'est pas une preuve** : la perte de
   l'entraînement descendait pendant que l'erreur de validation ne
   bougeait pas — il fallait regarder la **corrélation** et l'erreur
   **sur le test**, jamais la perte seule.

## 2. N-1 — le générateur : une période de quatre

### Le symptôme

Le réseau de valeur n'apprenait **rien** : l'erreur de validation
restait exactement à la valeur d'un prédicteur constant (RMSE 1,30
alors que la cible est dans `[-1, 1]`), et la corrélation sortie/cible
valait **+0,000** — un réseau parfaitement inconscient de l'échiquier.

### Le diagnostic

L'instrumentation a montré **0 unité active** sur 12 800 (la ReLU ne
laissait passer rien) et une moyenne de pré-activation à **−2,88** —
là où elle devait être centrée sur zéro. La cause : les poids
initialisés n'avaient pas une moyenne nulle. En remontant la chaîne :
le générateur pseudo-aléatoire ne variait pas.

`mcts::Rng` est un **xorshift64\*** annoncé, mais le décalage du milieu
était un `>> 25` au lieu d'un `<< 25` :

```rust
x ^= x >> 12;      // correct
x ^= x >> 25;      // FAUX : le xorshift64* canonique est x ^= x << 25
x ^= x >> 27;      // correct
```

Avec trois décalages à droite, la transformation de l'état n'est pas
réversible : l'état cycle sur un cycle de **4**. Le générateur ne
produisait que **quatre** valeurs, répétées indéfiniment :

```text
3154547314117558073, 2506398873287524326,
468725656381219356, 5192220531023863043,   <- et on recommence
```

La preuve que c'est bien une faute de transcription : `examples/leaf_probe.rs`
— une copie plus ancienne du même générateur — portait le `<< 25`
correct.

### Ce que le bug invalidait

* le tirage « au hasard » du MCTS (le choix parmi les enfants non
  visités) ne tirait que **quatre** valeurs : l'exploration de l'arbre
  était quasi déterministe ;
* la perturbation Gumbel de la racine (mode parallèle) était
  dégénérée ;
* le corpus d'auto-play de la tranche N1 n'avait **aucune** diversité.

Ce n'était pas un détail esthétique : c'est **la** cause de l'échec de
la première tentative d'entraînement.

### Le correctif

Une ligne (`<< 25`), plus deux tests de non-régression dans
`src/mcts.rs` : 10 000 tirages distincts, et le déterminisme (même
graine, même suite). Le core gelé n'est **pas** touché : `mcts::Rng`
n'appartient pas au core (`position`, `movegen`, `types`, `zobrist` sont
intacts). En revanche le **comportement du MCTS change** — c'est un
changement de moteur, et il est donc **mesuré** par un duel (§5).

## 3. N0 à N3 — le contrat, le corpus, le modèle, l'entraînement

### N0 — le contrat par lot

`eval::eval_batch(&[Position]) -> Vec<i32>` rend **exactement** les
valeurs de `eval_for_mover`, position par position (test d'identité sur
1 000 positions). C'est le contrat que l'inférence SIMD consomme : le
lot est évalué position par position, et la convention de signe ne
change pas.

### N1 — le collecteur de corpus

`examples/gen_positions` fait jouer au MCTS des parties d'auto-play et
écrit, par position : `zobrist | fen | résultat | ply | partie`.

Deux règles d'honnêteté, inscrites dans le code :

1. **une partie sans résultat est jetée** (limite de demi-coups
   atteinte) : l'arbitrer avec l'évaluation statique reviendrait à
   écrire la réponse dans la question ;
2. **la seule annotation est le résultat de la partie** — la valeur
   d'une recherche bruitée n'est pas une annotation (phase AB7 : le
   bruit de la valeur est de 104 cp par 2 plies).

Le corpus est **déterministe** : deux exécutions avec la même graine
produisent le fichier **identique** (vérifié, `cmp` sans différence).
Le format est texte, versionné, et le FEN fait un aller-retour exact
(test dans `src/corpus.rs`).

### N2 — le modèle

`src/nn.rs` : un perceptron à une couche cachée, CPU-only, sans
dépendance.

```text
h[j] = b1[j] + Σ_pièces W1[plan][case][j] + W_trait[trait][j]
h    = ReLU(h)
y    = b2 + Σ_j W2[j]·h[j]          (sortie linéaire, découpée à ±1)
```

* **forme creuse** : seules les ~32 cases occupées sont lues — la
  première couche est une **table de positions apprise** ;
* **49 345 paramètres** ;
* **AVX2 détecté à l'exécution**, repli scalaire : le résultat est
  **identique** dans les deux cas (même ordre d'addition), seul le
  débit change. Pas d'AVX-512 (l'EPYC de référence n'en a pas) ;
* **sortie linéaire** et non `tanh` : le `tanh` sature exactement sur
  les cibles ±1, son gradient s'annule, et l'apprentissage ne démarre
  pas (constaté, puis corrigé) ;
* **format de fichier** versionné, avec aller-retour testé.

### N3 — l'entraînement

`examples/train_nn` : Adam écrit à la main (aucune dépendance), lot de
32, mélange déterministe, **découpe train/test par partie** (jamais par
position — sinon les positions d'une même partie se répondent
mutuellement et l'erreur mesurée est une illusion).

Le **gate** est une comparaison honnête : l'erreur du réseau (RMSE sur
le test) contre l'erreur de l'**évaluation statique calibrée** — on
ajuste un scalaire `a` sur l'ensemble d'entraînement pour mettre
l'éval statique à la même échelle que la cible, puis on compare les
deux RMSE **sur le test**. Sans calibration, on comparerait deux échelles
différentes et le gate ne voudrait rien dire.

**L'instrument qui a sauvé la phase** : `--check-grad` compare le
gradient analytique au gradient par différences finies. Il a montré un
écart systématique de ×2,8 sur **tous** les paramètres : la ReLU n'était
pas appliquée avant la couche de sortie dans le backward, donc
l'entraînement optimisait une fonction *différente* de celle déployée.
Après correction, l'écart tombe à ~1e-6 (le bruit des différences
finies).

## 4. Les mesures

### 4.1 Le corpus

| corpus | étiquette | positions | parties | jetées |
|---|---|---|---|---|
| `models/corpus_v2.txt` | résultat de partie | 60 000 | 519 | 124 (19 %) |
| `models/corpus_v3.txt` | **valeur de la recherche** | 40 000 | 322 | 76 (19 %) |

Les parties jetées sont celles qui atteignent la limite de demi-coups :
elles n'ont pas de résultat, et l'arbitrer avec l'évaluation statique
reviendrait à écrire la réponse dans la question.

### 4.2 L'étiquette : deux essais, et pourquoi le premier ne pouvait pas marcher

| étiquette | réseau (test RMSE) | **éval statique calibrée** (test RMSE) | gate |
|---|---|---|---|
| résultat de partie | 0,787 (hidden 64) | **0,691** | ÉCHOUÉ |
| valeur de la recherche | 0,171 (hidden 16) | **0,132** | ÉCHOUÉ |

**Le premier essai ne pouvait pas marcher, et on peut le dire.** Le
résultat de partie est une annotation **très** bruyante : pour une
position équilibrée, le résultat de la partie est une pièce de pile ou
face, donc la variance de l'étiquette autour de la vraie valeur est de
l'ordre de 0,5. Or l'évaluation statique **déjà calibrée** atteint 0,69
— elle est **au plancher de ce bruit**. Il n'y a pas de signal à
extraire : un réseau de 49 345 paramètres ne peut pas faire mieux que
le bruit de l'étiquette. Le réseau **sur-apprend** (RMSE
d'entraînement 0,16 contre 0,79 sur le test) : il mémorise le bruit.

**Le second essai (la valeur de la recherche) est plus serré, et
c'est instructif** : l'étiquette continue est la **valeur de la racine
du MCTS** (une moyenne sur l'arbre, donc bien moins bruitée que le
résultat final). Mais les feuilles de ce MCTS sont... l'évaluation
statique. La valeur de la recherche est donc **l'évaluation statique
améliorée par la recherche** (les tactiques que la statique rate), et
l'écart entre les deux est **exactement** la part de la valeur que
l'évaluation statique manque. Un réseau **lisse** ne peut pas la
reproduire : il ne peut pas deviner, position par position, ce que la
recherche va trouver. D'où un RMSE de 0,171 pour le réseau contre 0,132
pour l'éval statique.

La conclusion de la mesure est double : la valeur ne peut
s'améliorer que si **la recherche** s'améliore, et la recherche
s'améliore grâce à une meilleure valeur. C'est la **boucle**
d'AlphaZero, et elle a besoin d'au moins un tour où l'étiquette est
*vraiment* meilleure que la statique — ici, elle ne l'est pas encore.

### 4.3 Ce que l'entraînement montre (la courbe)

* avec l'étiquette « résultat de partie » : la corrélation sortie/cible
  monte à 0,97 mais le **test** reste à 0,78-0,80 pendant que
  l'**entraînement** descend à 0,16 : la sur-apprentissage est
  manifeste ;
* avec l'étiquette « valeur de la recherche » : la corrélation atteint
  0,99 et le test se stabilise à 0,167-0,171 (l'écart
  entraînement/test reste raisonnable : 0,09 contre 0,17) ;
* le **mode plat** (une table de positions apprise, sans couche
  cachée) **n'apprend rien** (0,86, la corrélation à 0,005) : sans la
  non-linéarité, le modèle est **mal conditionné** (les poids des
  lignes et le poids de sortie ne sont définis qu'à un facteur près) et
  Adam — qui normalise chaque paramètre séparément — fait décroître le
  poids de sortie jusqu'à zéro. C'est un fait mesuré, pas une
  intuition : la sortie de la couche est désormais **figée à 1** dans
  ce mode.

### 4.4 Le prix à payer

La valeur apprise coûte **−18 % de débit** à la feuille : 478 848 nœuds
en 500 ms sans le réseau, 390 016 avec (mesure sur la position de
référence, moteur mono). C'est le prix de l'inférence (~220 ns par
feuille contre ~31 ns pour l'évaluation statique), et c'est lui qui rend
les tranches PERF P4 (arène compacte) et P5 (arbre partagé) nécessaires
avant de viser le lot SIMD.

### 4.5 L'instrument qui a sauvé la phase

`--check-grad` compare le gradient analytique au gradient par
différences finies. L'écart mesuré était de **×2,8 sur tous les
paramètres** : la ReLU n'était pas appliquée avant la couche de sortie
dans le backward, donc l'entraînement optimisait une fonction
*différente* de celle déployée. Après correction, l'écart tombe à
~1e-6 (le bruit des différences finies). Sans cet instrument, on
aurait cherché un réglage de taux d'apprentissage au lieu d'un défaut.

## 6. Ce qu'on retient

1. **Un générateur pseudo-aléatoire n'est pas un détail** : une période
   de quatre a suffi à rendre le projet ** incapable d'apprendre**,
   sans que rien ne semble anormal (le moteur jouait, le duel marchait,
   les tests passaient). La régression doit être un **test**, pas une
   relecture ;
2. **le protocole d'entraînement doit être vérifiable** : la
   vérification numérique du gradient coûte dix lignes et a sauvé la
   phase ;
3. **la perte d'entraînement ne prouve rien** : il faut l'erreur **sur
   le test**, la **corrélation**, et une **comparaison calibrée** avec la
   référence ;
4. **une métrique de débit n'est pas une métrique de force** (leçon
   d'AB8, qui reste vraie) : et l'inverse aussi — une valeur apprise
   doit gagner **au duel**, pas seulement en erreur d'évaluation.
